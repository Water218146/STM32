### 技术栈选择

| 层级 | 技术 | 原因 |
|------|------|------|
| **后端运行时** | Node.js | JavaScript 全栈统一，异步 I/O 高效 |
| **HTTP 服务器** | Express | 轻量级，生态成熟，易于扩展 |
| **WebSocket 库** | ws | 原生协议，性能优异，无额外封装 |
| **环境变量** | dotenv | 配置分离，安全管理敏感信息 |
| **前端结构** | HTML5 | 语义化，标准化 |
| **前端样式** | CSS3（独立文件） | 样式分离，易于维护和主题切换 |
| **前端逻辑** | JavaScript ES6+ | 原生实现，无框架依赖 |

## 🔑 核心约束与原则

### 必须遵守的约束

1. **前端无框架约束**
   - ❌ 禁止使用 React、Vue、Angular 等框架
   - ✅ 使用原生 HTML、CSS、JavaScript
   - **原因**：符合奥卡姆剃刀原则，降低复杂度，减少学习成本

2. **CSS 独立文件约束**
   - ❌ 禁止在 HTML 中嵌入 `<style>` 标签
   - ❌ 禁止使用内联样式（除非动态样式必需）
   - ✅ 所有样式必须写在 `frontend/css/style.css`
   - **原因**：样式与结构分离，便于维护和主题切换

3. **文件路径约束**
   - ✅ Windows 环境，使用反斜杠路径（`\`）
   - ✅ 所有文件操作使用绝对路径
   - **原因**：避免路径解析错误

4. **编码约束**
   - ✅ 所有文件使用 UTF-8 编码
   - ✅ 代码注释使用简体中文
   - **原因**：中文注释便于理解和维护

### 设计原则

1. **奥卡姆剃刀原则**
   - 优先选择简单方案
   - 不为未来可能不会发生的需求过度设计
   - 每增加一个依赖都要问"真的必要吗？"

2. **前后端分离原则**
   - 后端只负责 WebSocket 通信和静态文件服务
   - 前端完全独立，可单独部署到 CDN
   - API 协议清晰定义，便于扩展

3. **可扩展性原则**
   - 代码预留扩展点（如消息协议字段）
   - 配置与代码分离（.env 管理）
   - 模块化设计，便于后续重构

## 🎨 架构决策记录（ADR）

### ADR-001: 为什么选择前后端分离？

**日期**: 2026-01-23

**背景**：需要构建一个可扩展的终端管理系统。

**决策**：采用前后端分离架构。

**理由**：
- ✅ 便于后续集成内网穿透服务（frp/ngrok）
- ✅ 前端可以单独部署到 CDN，提高访问速度
- ✅ 后端可以独立扩展（负载均衡、集群）
- ✅ 前后端团队可以并行开发

**后果**：
- 增加了部署复杂度（但通过 Express 托管静态文件简化）
- 需要定义清晰的 API 协议

---

### ADR-002: 为什么前端不使用框架？

**日期**: 2026-01-23

**背景**：需要选择前端技术栈。

**决策**：前端不使用任何框架（React、Vue 等），使用原生 JavaScript。

**理由**：
- ✅ 项目规模较小，不需要框架的复杂功能
- ✅ 降低学习成本和依赖体积
- ✅ 更快的加载速度（无框架运行时）
- ✅ 符合奥卡姆剃刀原则：如无必要，勿增实体

**后果**：
- 需要手动管理 DOM 操作
- 代码量略有增加（但仍在可控范围）

**未来考虑**：如果项目复杂度大幅增加，可重构为框架方案。

---

### ADR-003: 为什么后端集成静态文件服务？

**日期**: 2026-01-23

**背景**：需要决定如何部署前端文件。

**决策**：后端 Express 服务器托管前端静态文件。

**理由**：
- ✅ 简化部署，单一服务器即可运行完整系统
- ✅ 避免跨域问题（同源策略）
- ✅ 方便本地开发和测试
- ✅ 单一端口对外服务

**后果**：
- 后端服务器需要处理静态文件请求（但负载不大）

**未来考虑**：生产环境可以将静态文件部署到 CDN。

---

### ADR-004: 为什么选择 ws 而不是 socket.io？

**日期**: 2026-01-23

**背景**：需要选择 WebSocket 库。

**决策**：使用原生 ws 库，而不是 socket.io。

**理由**：
- ✅ ws 是原生 WebSocket 协议，更轻量（~10KB vs ~200KB）
- ✅ 性能更高，无额外封装层
- ✅ 协议标准，兼容任何 WebSocket 客户端
- ✅ 符合奥卡姆剃刀原则

**后果**：
- 需要手动实现心跳检测（已实现）
- 不支持自动降级到轮询（但现代浏览器都支持 WebSocket）

**未来考虑**：如果需要自动降级或更多特性，可迁移到 socket.io。

- 缺点：免费版域名会变化

- 优点：自主可控，稳定性高，可自定义域名
- 缺点：需要云服务器
- 适用：生产环境和长期项目

**实现步骤**：
1. ✅ 选择内网穿透方案（cpolar 先快速验证，后续可迁移到 frp）

## 📐 代码规范

### 命名规范

- **变量/函数**: 驼峰式（camelCase）
  ```javascript
  let clientId = 'client_001';
  function sendMessage() { ... }
  ```

- **常量**: 大写下划线（UPPER_SNAKE_CASE）
  ```javascript
  const WS_HEARTBEAT_INTERVAL = 30000;
  ```

- **类名**: 帕斯卡式（PascalCase）
  ```javascript
  class WebSocketManager { ... }
  ```

- **文件名**: 小写连字符（kebab-case）或驼峰式
  ```
  server.js
  app.js
  style.css
  ```

### 注释规范

- **函数注释**：使用 JSDoc 风格
  ```javascript
  /**
   * 广播消息到所有客户端
   * @param {Object} message - 消息对象
   * @param {string} excludeClientId - 要排除的客户端ID
   */
  function broadcast(message, excludeClientId) { ... }
  ```

- **代码块注释**：使用 `// ====` 分隔符
  ```javascript
  // ==================== 连接管理 ====================
  ```

- **单行注释**：解释复杂逻辑
  ```javascript
  // 检查客户端是否还活着
  if (ws.isAlive === false) { ... }
  ```

## ❓ 常见问题（FAQ）

### Q1: 为什么不使用 TypeScript？

**A**: 当前阶段项目规模较小，使用 JavaScript 可以降低复杂度和编译成本。如果后续项目规模扩大，可以考虑迁移到 TypeScript。

---

### Q2: 为什么不使用数据库？

**A**: 第一阶段专注于建立通信基础，暂不需要持久化。第四阶段将集成数据库实现消息历史和用户管理。

---

### Q3: 性能瓶颈在哪里？

**A**:
- **当前架构**：单进程 Node.js，理论上可支持数千并发连接
- **潜在瓶颈**：单点故障，无负载均衡
- **解决方案**：后续引入 Redis 做消息队列，PM2 做进程管理，Nginx 做反向代理

---

### Q4: 如何保证安全性？

**A**:
- **当前实现**：HTML 转义防 XSS，输入验证
- **后续计划**：
  - HTTPS/WSS 加密传输
  - JWT 认证
  - 消息签名防篡改
  - 频率限制防 DDoS

---

### Q5: 如何扩展到企业级应用？

**A**:
1. 引入 Redis 做会话存储和消息队列
2. 引入 MongoDB/PostgreSQL 做数据持久化
3. 引入 Nginx 做反向代理和负载均衡
4. 引入 Docker/Kubernetes 做容器化部署
5. 引入日志系统（ELK Stack）做监控和分析
